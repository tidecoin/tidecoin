## Data directory location

The data directory is the default location where the Tidecoin Core files are stored.

1. The default data directory paths for supported platforms are:

Platform | Data directory path
---------|--------------------
Linux    | `$HOME/.tidecoin/`
macOS    | `$HOME/Library/Application Support/Tidecoin/`
Windows  | `%LOCALAPPDATA%\Tidecoin\` <sup>[\[1\]](#note1)</sup>

2. A custom data directory path can be specified with the `-datadir` option.

3. All content of the data directory, except for `tidecoin.conf` file, is chain-specific. This means the actual data directory paths for non-mainnet cases differ:

Chain option                     | Data directory path
---------------------------------|------------------------------
`-chain=main` (default)          | *path_to_datadir*`/`
`-chain=test` or `-testnet`      | *path_to_datadir*`/testnet/`
`-chain=regtest` or `-regtest`   | *path_to_datadir*`/regtest/`

### Block-storage metadata

The block-index database supports file numbers 0 through 1,048,575. This local
resource limit permits about 48 MiB of file-info entries on 64-bit builds,
excluding the vector's spare capacity. It corresponds to roughly 128 TiB of
normal-sized block files over their lifetime; pruning removes files but does not
reset their numbering. The test-only
`-fastprune` option uses smaller files. The limit is not a consensus rule or a
change to the database encoding. An over-limit value in stored metadata stops
startup with the file number and supported maximum. Because the block index may
be damaged, the GUI offers a user-approved rebuild; daemon users can restart
with full `-reindex`. This is not an automatic rebuild. `-reindex-chainstate`
does not repair block-index metadata. Rebuilding does not raise the limit: actual
file allocation or reindexing that reaches an unsupported file number stops with
a fatal error, and an interrupted reindex remains marked as incomplete.

Malformed last-file metadata or block references beyond the loaded file records
cause a database-load error instead of an unsafe allocation or array access.
Rebuilding with `-reindex` can repair a damaged block index when the block files
are intact; pruned data may need to be downloaded again. An absent last-file
record retains the existing recovery scan from file zero. The node does not
clamp or rewrite an invalid value automatically.

`blocks/xor.dat` contains exactly eight bytes. Keep it with the block and undo
files when copying or backing up those files. It is an obfuscation pattern, not
a wallet key. Replacing it does not convert existing block files to a new pattern.

New XOR keys are saved through `.xor.dat.tmp`, with checked file synchronization,
close and rename, followed by directory synchronization where supported, before
block data is written. A failed directory synchronization stops initialization;
if no block or undo files exist yet, the next start retries that synchronization
using the saved key. A leftover temporary file does not change first-run key
selection and is not used as a recovery key.

Invalid-length or unreadable keys cause an error naming the file. First check
file access and storage health. If the key is damaged, restore the original key
belonging to those block files from a backup. Otherwise, rebuild the affected
local blockchain data from the network, preserving wallets and configuration.
`-reindex` cannot decode obfuscated files using a different key.

For compatibility, an existing blocks directory without `xor.dat` still receives
an all-zero pattern. This supports old unobfuscated data, but does not detect a
lost key for obfuscated data. Automatic lost-key detection and recovery are not
provided. Do not delete `xor.dat` while retaining files obfuscated with it.

The synchronization helpers use the operating system's available guarantees.
Unsupported synchronization is tolerated; Windows has no separate directory
synchronization here. Storage corruption and hardware that does not honor flush
requests remain outside those guarantees.

## Multi-wallet environment

Wallets are SQLite databases.

1. Each user-defined wallet named "wallet_name" resides in the `wallets/wallet_name/` subdirectory.

2. The default (unnamed) wallet resides in `wallets/` subdirectory; if the latter does not exist, the wallet resides in the data directory.

3. A wallet database path can be specified with the `-wallet` option.

4. `wallet.dat` files must not be shared across different node instances, as that can result in key-reuse and double-spends due to the lack of synchronization between instances.

5. Any copy or backup of the wallet should be done through a `backupwallet` call in order to update and lock the wallet, preventing any file corruption caused by updates during the copy.


### SQLite database based wallets

Subdirectory | File                 | Description
-------------|----------------------|-------------
`./`         | `wallet.dat`         | Personal wallet (a SQLite database) with keys and transactions
`./`         | `wallet.dat-journal` | SQLite Rollback Journal file for `wallet.dat`. Usually created at start and deleted on shutdown. A user *must keep it as safe* as the `wallet.dat` file.


## GUI settings

`tidecoin-qt` uses [`QSettings`](https://doc.qt.io/qt-6/qsettings.html) class; this implies platform-specific [locations where application settings are stored](https://doc.qt.io/qt-6/qsettings.html#locations-where-application-settings-are-stored).


### Berkeley DB database based wallets

Subdirectory | File(s)           | Description
-------------|-------------------|-------------
`database/`  | BDB logging files | Part of BDB environment; created at start and deleted on shutdown; a user *must keep it as safe* as personal wallet `wallet.dat`
`./`         | `db.log`          | BDB error file
`./`         | `wallet.dat`      | Personal wallet (a BDB database) with keys and transactions
`./`         | `.walletlock`     | BDB wallet lock file

## Filesystem recommendations

When choosing a filesystem for the data directory (`datadir`) or blocks directory (`blocksdir`) on **macOS**,the `exFAT` filesystem should be avoided.
There have been multiple reports of database corruption and data loss when using this filesystem with Tidecoin Core.
